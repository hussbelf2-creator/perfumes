# منصة إنشاء البراندات العطرية

واجهة React + Vite + Tailwind لمنصة تقود العميل من الفكرة إلى إطلاق براند عطري.

## التشغيل

```bash
npm install
npm run dev        # http://localhost:3000
npm run build      # المخرجات في out/
npm run type-check
npm run lint
```

## قبل الإطلاق — قائمة إلزامية

1. **بيانات العلامة والتواصل**: عدّل `src/config/site.ts` (الاسم، البريد، الجوال، واتساب، الحسابات الاجتماعية).
   أي حقل فارغ يُخفى تلقائياً، وزر واتساب العائم يظهر بمجرد إدخال الرقم.
2. **الشعار**: انقل الشعار إلى `public/` وحدّث `SITE.logo` و`index.html`؛ هو مستضاف حالياً لدى Readdy.
3. **الصور**: صور الموقع مولّدة من `readdy.ai/api/search-image` — استبدلها بصور حقيقية في `public/`.
4. **Supabase** (المصادقة الحقيقية وكل البيانات والملفات): اتبع قسم «ربط الباك إند» أدناه، وأنهِه بـ`npm run check:backend` دون أخطاء.
5. **الصفحات القانونية**: أدخل الاسم النظامي والسجل التجاري والرقم الضريبي في «محتوى الموقع ← التواصل والحسابات»، ثم راجع نصوص «الصفحات القانونية» مع مستشار قانوني. بوابة الدفع تطلب الروابط `/privacy` و`/terms` و`/refund`.

## أوضاع التشغيل

| الوضع | متى | المصادقة | النماذج |
|---|---|---|---|
| تجريبي | بدون مفاتيح Supabase | حسابات محلية في المتصفح (كلمة المرور مُجزّأة ومُتحقق منها) | تُرسل إلى نقاط Readdy الحالية |
| إنتاج | مع مفاتيح Supabase | Supabase Auth + تأكيد البريد + استعادة كلمة المرور | تُحفظ في جدول `leads` |

> حماية `/admin` في الواجهة تمنع الوصول العرضي فقط. الحماية الفعلية للبيانات تأتي من سياسات RLS في Supabase.

## ربط الباك إند (Supabase)

ملف واحد ينشئ كل شيء: `supabase/schema.sql` (الجداول الـ19، سياسات RLS، الدوال والمُشغّلات، مصفوفة الصلاحيات، وحاويات الملفات). قابل لإعادة التنفيذ بأمان بعد كل تحديث.

1. **أنشئ مشروعاً** على supabase.com (يُفضّل منطقة قريبة من الخليج، مثل Frankfurt أو Mumbai).
2. **طبّق المخطط** — إمّا بلصق الملف في SQL Editor، أو من الطرفية:
   ```bash
   SUPABASE_DB_URL="postgresql://postgres.<ref>:<password>@<host>:5432/postgres" npm run db:apply
   ```
   (الرابط من Project Settings ← Database ← Connection string ← Session pooler.)
3. **المتغيرات** — في `.env.local` محلياً، وفي Vercel ← Settings ← Environment Variables:
   | المتغير | أين يُستخدم |
   |---|---|
   | `VITE_SUPABASE_URL`، `VITE_SUPABASE_ANON_KEY` | الواجهة (عامة بطبيعتها؛ الحماية من RLS) |
   | `SUPABASE_URL`، `SUPABASE_ANON_KEY`، `SUPABASE_SERVICE_ROLE_KEY` | دوال الخادم وسكربت الفحص فقط — **لا بادئة `VITE_` أبداً** |
4. **الدخول** (Authentication):
   - فعّل **Confirm email** — ربط المشاريع بالعميل يتم بالبريد، فلا بد أن يكون مؤكَّداً.
   - URL Configuration: اجعل Site URL نطاقك، وأضف `https://<نطاقك>/**` و`http://localhost:3000/**` في Redirect URLs.
5. **عيّن المالك**: سجّل حسابك من الموقع، ثم في SQL Editor:
   `update public.profiles set role = 'owner' where email = 'you@example.com';`
   وبعدها امنح أدوار الفريق من `/admin/team`.
6. **افحص الربط**:
   ```bash
   npm run check:backend
   ```
   يتحقق من الاتصال والمفاتيح، وجود الجداول والصلاحيات، أن الزائر لا يقرأ بيانات العملاء ولا يكتب على المحتوى، أن النماذج تصل للوارد، أن حاوية `projects` خاصة والبقية عامة، وإعدادات تأكيد البريد ووجود مالك. يخرج برمز خطأ عند أي مشكلة (صالح للـCI).

> الروابط المخزنة للصور والنماذج تُقبل بـ`https` فقط (في الواجهة وفي قيود قاعدة البيانات). عند التطوير على Supabase محلي (`supabase start`) شغّله خلف https أو ارفع الصور على مشروع سحابي.

ما تم التحقق منه آلياً على Supabase حقيقي (Postgres + Auth + PostgREST + Storage): رسالة زائر تصل للوارد وتُنشئ عميلاً، المسودة لا تظهر للزوار والنشر يظهر فوراً، رفع أعمال المبدعين للحاوية العامة، مشروع لعميل لم يسجّل بعد يُربط عند تسجيله، ملفاته خاصة تُعرض بروابط موقّعة، طلب التعديل والاعتماد والنسخ والرسائل وسجل التدقيق، حفظ تصاميم الاستوديو، وعزل العملاء عن بعضهم.

## اللغتان العربية والإنجليزية

- السياق في `src/i18n/`: `useI18n()` يعطي `t("عربي", "English")` و`pick({ ar, en })` وتنسيق الأرقام والتواريخ والريال.
- زر التبديل يقلب `lang` و`dir` على مستوى الصفحة، ويُحفظ الاختيار في المتصفح. الرابط `?lang=en` يفتح الموقع بالإنجليزية.
- استخدم الخصائص المنطقية في Tailwind (`ms-`, `pe-`, `start-`, `text-start`, `border-s`) بدل `left/right` حتى تنقلب الواجهة تلقائياً.
- الأقسام غير المترجمة بعد (المعالجات، لوحة الإدارة، صفحات العميل القديمة) ملفوفة بـ `components/ui/ArabicOnly.tsx`: تبقى عربية مع تنبيه في الوضع الإنجليزي.
- بيانات الخدمات والأسئلة والنماذج كلها ثنائية في `src/data/`.

## نقاط الدخول: مكالمة الاكتشاف وعينة الاكتشاف

| الصفحة | ما تفعله | الإعداد |
|---|---|---|
| `/book` | حجز مكالمة مجانية (20 دقيقة): يوم ووقت بتوقيت الرياض، قناة التواصل، المسار المهتم به؛ ثم إضافة للتقويم (Google / ‎.ics) | `DISCOVERY_CALL` في `src/config/offers.ts` (الأيام، الأوقات، المدة) |
| `/discovery-kit` | اختبار من 4 أسئلة ← 3 اتجاهات عطرية مقترحة ← طلب عينة مدفوعة بالشحن | `DISCOVERY_KIT` (السعر 750 ر.س، عدد القوارير، مدة احتساب المبلغ من المشروع) |

- الطلبات تُرسل عبر `submitForm("booking" | "kit")` ومعها الحقل `request_type` (`discovery_call` / `discovery_kit`) لتمييزها في البريد أو جدول `leads`.
- نقاط إرسال مستقلة اختيارية: `VITE_BOOKING_FORM_URL` و`VITE_KIT_FORM_URL`. إن لم تُضبط تُستخدم نقطة نموذج التواصل.
- **التقويم**: الأوقات الداخلية ليست مرتبطة بتوفر فعلي (الفريق يؤكد كل حجز). اضبط `VITE_BOOKING_URL` برابط Cal.com أو Calendly ليحل زر "افتح التقويم" محل منتقي المواعيد الداخلي.

## الدفع الإلكتروني (مويسر)

عينة الاكتشاف تُدفع عبر [Moyasar](https://moyasar.com): مدى، فيزا، ماستركارد، Apple Pay، وSTC Pay.

```
المتصفح                         مويسر                    Vercel Function
  │ نموذج الطلب → رقم KIT-XXXXXX   │                          │
  │ ── نموذج الدفع (pk_) ────────▶ │                          │
  │ ◀── إعادة توجيه ?id=…&status=… │                          │
  │ /discovery-kit/paid ── GET /api/payments/verify?id= ───▶ │ ── (sk_) يجلب الدفعة
  │ ◀──────────────── { paid } يطابق الحالة + المبلغ + العملة │
```

**لا نثق برابط العودة**: `status=paid` في الرابط قابل للتلاعب؛ القرار يأتي من الخادم بعد جلب الدفعة بالمفتاح السري ومطابقة المبلغ (`KIT_PRICE_HALALAS`) والعملة.

### التفعيل
1. أنشئ حساباً في مويسر، وخذ المفاتيح التجريبية أولاً (`pk_test_` و`sk_test_`).
2. في Vercel → Environment Variables:
   - `VITE_MOYASAR_PUBLISHABLE_KEY` (عام، يُبنى في الواجهة)
   - `MOYASAR_SECRET_KEY` (سري، للخادم فقط — **بدون** بادئة `VITE_`)
   - `KIT_PRICE_HALALAS` = سعر العينة × 100 (يجب أن يطابق `DISCOVERY_KIT.price`)
   - اختياري لتسجيل المدفوعات: `SUPABASE_URL` و`SUPABASE_SERVICE_ROLE_KEY` بعد تنفيذ جدول `payments` من `supabase/schema.sql`.
3. لـ Apple Pay: سجّل نطاق الموقع في لوحة مويسر.
4. اختبر بالبطاقة `4111 1111 1111 1111`، ثم بدّل للمفاتيح الحية.

بدون المفتاح العام يعود الطلب لمسار "سنتواصل معك لإتمام الدفع" تلقائياً، فلا يتعطل شيء.

| الملف | الدور |
|---|---|
| `src/config/payments.ts` | التفعيل، طرق الدفع، نسخة مكتبة مويسر |
| `src/lib/payments.ts` | تحميل المكتبة عند الحاجة، التحقق، حفظ الطلب المعلّق لإعادة المحاولة |
| `src/components/feature/PaymentForm.tsx` | غلاف نموذج الدفع ثنائي اللغة مع حالات التحميل والخطأ |
| `src/pages/discovery-kit/Paid.tsx` | صفحة العودة: نجاح بإيصال، أو فشل مع إعادة محاولة |
| `api/payments/verify.ts` | التحقق على الخادم + تسجيل اختياري في Supabase |

## لوحة الإدارة (المرحلة 1: الأساس وCRM)

لوحتان منفصلتان تماماً، لكلٍّ منها حماية وتخطيط وحزمة كود مستقلة:

| | المسار | لمن | الحماية |
|---|---|---|---|
| لوحة الإدارة | `/admin/*` | فريق المنصة (أي دور غير «عميل») | `src/admin/AdminApp.tsx` + `RequirePerm` لكل صفحة |
| لوحة العميل | `/account/*` (كانت `/dashboard`، وتُحوَّل تلقائياً) | العملاء فقط | `AuthGuard` يحوّل الموظف إلى `/admin` |

### الأدوار والصلاحيات
المصفوفة في `src/lib/rbac.ts`، ومكررة في جدول `role_permissions` في `supabase/schema.sql`، وهو مصدر الحماية الفعلية.

| الدور | يرى ويعمل على |
|---|---|
| مالك | كل شيء، ويمنح دور المالك |
| مدير | كل شيء عدا إدارة الملاك |
| مبيعات | العملاء والطلبات والمراحل والمدفوعات، **بدون** إسناد العملاء أو سجل التدقيق |
| إنتاج | عرض العملاء والطلبات للتجهيز والشحن، ومهامه |
| مصمم / محرر | مهامهم فقط الآن، وأدواتهم تأتي في المراحل 2 إلى 6 |

قواعد ثابتة في قاعدة البيانات:
- لا أحد يغيّر دوره أو يعطّل حسابه بنفسه.
- المالك وحده يدير الملاك، ولا يمكن أن تبقى المنصة بلا مالك نشط.
- الحساب المعطّل يفقد صلاحياته فوراً.

### الصفحات
- **نظرة عامة**: طلبات الأسبوع، قيمة الصفقات المفتوحة، نسبة الإغلاق، المحصّل، ما يحتاج انتباهك، مكالمات الأسبوع.
- **صندوق الوارد**: الحجوزات وطلبات العينة والرسائل، مع واتساب/اتصال/بريد/تقويم بنقرة، والإسناد والحالة والملاحظات.
- **مراحل البيع**: لوحة سحب وإفلات (ومن لوحة المفاتيح عبر قائمة «نقل إلى»).
- **العملاء** وملف كل عميل: سجل زمني، تسجيل مكالمة/ملاحظة/اجتماع، مهام، طلبات، مدفوعات، وتصدير CSV.
- **المهام**: متأخرة / اليوم / القادمة، لي أو للفريق.
- **المدفوعات**: من جدول `payments` الذي تكتبه دالة التحقق من مويسر.
- **الفريق والصلاحيات** و**سجل التدقيق**.

### كيف تصل البيانات
- كل طلب من نماذج الموقع يُربط تلقائياً بعميل (بالبريد أو الجوال) عبر مُشغّل في قاعدة البيانات.
- تغييرات المرحلة والإسناد والقيمة تُسجَّل في السجل الزمني وسجل التدقيق **بمُشغّلات**؛ لا يمكن تجاوزها أو حذفها من المتصفح.

### التفعيل على Supabase
راجع «ربط الباك إند» أعلاه؛ بعد تعيين المالك ادخل `/admin/team` وامنح الأدوار لبقية الفريق بعد تسجيلهم.

### الوضع التجريبي
- بدون Supabase تعمل اللوحة على بيانات نموذجية في المتصفح (`src/admin/data/seed.ts`)، بنفس قواعد الصلاحيات (`rules.ts`).
- زر «دخول كفريق المنصة» في صفحة الدخول يتيح تجربة كل دور، وقائمة «جرّب كدور» في أعلى اللوحة تبدّل بينها.
- الطلبات التي ترسلها من نماذج الموقع تظهر في صندوق الوارد.

### تحويل الصورة إلى نموذج 3D (`src/studio/profile.ts`)
1. يُكتشف لون الخلفية من إطار الصورة، أو الشفافية في PNG المقصوص.
2. لكل صف تُحدَّد أطراف الجسم، فنصف العرض هو نصف القطر عند ذلك الارتفاع.
3. ينظّف مرشح وسيط وتنعيم الحواف، ويُحَدّ ظل القاعدة تلقائياً حتى لا يصبح "صحناً" تحت العبوة.
4. يُقاس كل شيء بالمليمتر من الارتفاع الحقيقي الذي يدخله المصمم.
5. يُبنى المجسم بتدوير مقطع عرضي (دائري، أو مربع بزوايا ناعمة، أو بيضاوي) على طول المقطع الجانبي، بمنحنى رتيب لا يتجاوز النقاط (`geometry.ts`).

**حدود الطريقة:** تعمل بدقة مع العبوات المتناظرة حول محورها (أغلب عبوات العطر) ومع المربعة والبيضاوية؛ الصورة تعطي العرض، والعمق يحدده المصمم. أما الأشكال المنحوتة غير المتناظرة فتحتاج ملف 3D من المصمم أو خدمة ذكاء اصطناعي.

**فحص المقياس:** يحسب المحرر سعة العبوة حتى الحافة من الشكل، ويحذّر إن خرجت عن 105–130% من السعة الاسمية؛ وهذا يكشف خطأ إدخال الارتفاع.

### العرض
- **three.js:** زجاج بنفاذية وانكسار ولون امتصاص، وسائل داخل الزجاج، وأغطية معدنية وخشبية وسيراميك، وظل ناعم.
- **الحالة في الرابط** (`?b=&c=&g=&cf=&l=&f=`)، فيمكن مشاركة أي تركيبة.
- **حفظ صورة PNG**، و**«ناقش هذه التركيبة مع خبير»** يفتح حجز مكالمة مع ملخص التصميم في الملاحظات.
- **الواقع المعزز:** تصدير GLB بالمقاييس الحقيقية (متر)، ثم `@google/model-viewer` (WebXR على أندرويد وQuick Look على آيفون). يُحمَّل عند الطلب فقط.
- three.js وmodel-viewer في حزم منفصلة؛ لا يحمّلها زوار بقية الموقع.

### قاعدة البيانات
- جدول `packaging_models` في `supabase/schema.sql`: الزوار يرون المنشور فقط، والكتابة لـ `studio.manage`.
- النشر والإضافة والحذف تُسجَّل في سجل التدقيق.
- كتالوج البداية (4 عبوات و4 أغطية) مولَّد من `src/studio/seed.ts`، وسعاتها مطابقة لأشكالها.

### منتج من صورة بالذكاء الاصطناعي (`/admin/studio/ai`)
للأشكال المعقدة أو المنحوتة، وللمنتج كاملاً بغطائه وتفاصيله وألوانه. ينتج ملف GLB يُعرض للعميل كما هو، مع التدوير والتكبير والواقع المعزز.

```
المصمم (المتصفح)              api/ai3d.ts (Vercel)                  المزوّد
  صورة مصغّرة (≤1024px) ──POST─▶ يتحقق: توكن + has_perm('studio.manage')
                                 ─────────────────────────────────▶ Meshy / fal.ai
  ◀── jobId (202)                 يسجّل المهمة في ai3d_jobs
  كل 3 ثوانٍ ──GET?id=──────────▶ يسأل المزوّد عن الحالة والتقدّم
                                 عند النجاح: ينزّل GLB (+USDZ من Meshy)، يتحقق من توقيع glTF،
                                 ويرفعه إلى Supabase Storage (حاوية models) لأن روابط المزوّد مؤقتة
  ◀── glbUrl دائم ──────────────
  معاينة 3D ← حفظ في الكتالوج (source = 'ai')
```

**التفعيل:**
1. أنشئ حساباً لدى [Meshy](https://www.meshy.ai) (الافتراضي) أو [fal.ai](https://fal.ai).
2. في Vercel أضف: `AI3D_PROVIDER` و`MESHY_API_KEY` (أو `FAL_KEY`)، و`SUPABASE_URL` و`SUPABASE_ANON_KEY` و`SUPABASE_SERVICE_ROLE_KEY`.
3. نفّذ `supabase/schema.sql`؛ ينشئ جدول `ai3d_jobs` وحاوية `models`.

**الحماية:**
- المفتاح على الخادم فقط.
- لا يُرسَل طلب مدفوع إلا لمستخدم بصلاحية `studio.manage`.
- الصورة محدودة بـ 6 ميغابايت، والنموذج بـ 60 ميغابايت.
- تُقبل روابط https فقط.
- حالة المهام لا تُكتب من المتصفح.

**الوضع التجريبي:** بدون خادم ومفتاح تعمل الصفحة بمحاكاة محلية واضحة التسمية (نموذج من المقطع مكسوّ بالصورة) لتجربة المسار كاملاً، والملفات في IndexedDB.

**ملاحظة:** واجهات المزوّدين تتغير؛ أسماء الحقول في `api/ai3d.ts` مأخوذة من وثائقهم، ويجب تأكيدها بطلب حقيقي واحد قبل الإطلاق (مثل `model_urls.glb` في Meshy و`model_glb` في TRELLIS 2).

## محرر الملصق (المرحلة 3)
في استوديو العبوة (`/studio-3d`) تبويب «الملصق». يصمّم فيه العميل ملصقه ويراه ملفوفاً على العبوة ثلاثية الأبعاد مباشرة.

| | |
|---|---|
| **قوالب** | بسيط، كلاسيكي عربي، فاخر بالذهب، عصري، كرافت — مقاساتها تُحسب من شكل العبوة |
| **النصوص** | البراند، اسم العطر، سطر التفاصيل · 5 خطوط (Readex، Plex، أميري، ريم كوفي، Playfair) · الحجم بالمليمتر · تصغير تلقائي ليبقى النص داخل الملصق |
| **الفويل** | ذهبي/فضي/نحاسي للنصوص والشعار والإطار — معدني حقيقي في المعاينة (يلمع مع الحركة) عبر خريطة خامة منفصلة |
| **الشعار** | PNG/SVG/JPG، يُصغَّر محلياً، وتُفسح له النصوص مكاناً تلقائياً |
| **الورق** | أبيض، كريمي، كرافت (بألياف)، أسود، شفاف (طباعة مباشرة)، لون مخصص · مطفأ أو لامع |
| **الشكل والمقاس** | مستطيل، دائري الزوايا، بيضاوي، قوس · العرض والارتفاع والموضع بالمليمتر داخل منطقة الجسم |

**الدقة الهندسية** (`src/studio/label/geometry.ts`):
- العرض يُقاس **بطول القوس على سطح العبوة**، فملصق 50 مم يبقى 50 مم على الدائري والمربع والبيضاوي.
- أخذ عينات تكيّفي يمنع تمطّط النص في منتصف الواجهات المسطحة.
- منطقة الملصق تُحسب من المقطع (فوق القاعدة وتحت الكتف). وعند تغيير العبوة يُعاد ضبط الملصق ليبقى داخلها.

**ملف الطباعة** (`pdf.ts`):
- PDF بالمقاس الحقيقي، 300 نقطة/بوصة، هامش قص 3 مم وعلامات قص.
- **خط القص في صفحة ثانية مستقلة** بلون ماجنتا.
- يمكن أيضاً تصدير صورة PNG للملصق.

**الحفظ:**
- التصميم (مع الشعار) يُحفظ في متصفح العميل تلقائياً.
- ملخصه يُرفق بطلب «ناقش هذه التركيبة مع خبير».
- يُضمَّن في ملف الواقع المعزز.

**الأداء:** العارض يرسم عند الحاجة فقط: عند السحب أو الدوران التلقائي أو تغيّر المشهد، ويتوقف حين يخرج من الشاشة. الزجاج يكلّف تمريرتَي رسم لكل إطار، فالرسم المستمر كان يستهلك البطارية بلا داعٍ.

## مكتبة العلب الكرتونية (المرحلة 4)
تبويب «العلبة» في `/studio-3d` (ويُفتح مباشرة بالرابط `?tab=box`). يختار فيه العميل نوع العلبة ومقاسها وخامتها ونصوصها، ويرى العلبة تُطوى أمامه ثلاثية الأبعاد، ثم يحمّل ملفات المصنع.

| النوع | الخامة | ملاحظات |
|---|---|---|
| علبة بلسان (Reverse Tuck End) | كرتون 0.45 مم | ألسنة غبار، لسان إغلاق مستدير، شريط لصق مائل |
| علبة صلبة بغطاء | كرتون رمادي 2 مم | قاعدة وغطاء منفصلان، ألسنة زوايا |
| علبة درج | 0.6 مم | غلاف وصينية بفتحة إبهام. يستلقي فيها المنتج |
| علبة مغناطيسية | 2 مم | غطاء متصل بالظهر مع لسان أمامي |
| أسطوانة ورقية | 1.5 مم | جسم وغطاء ملفوفان مع قرصين |

**مصدر واحد للحقيقة** (`src/studio/box/dielines.ts`): كل علبة شجرة ألواح ومفصلات. من هذه الشجرة نفسها يُشتق:
1. **المخطط المسطّح.**
2. **خطوط القص**: حواف الألواح بعد طرح المفصلات.
3. **خطوط التكسير**: المفصلات نفسها.
4. **المجسم المطوي**: كل مفصل محور دوران. الطي يتم بمراحل (الجدران ثم الألسنة ثم الأغطية).

**التصميم** (`art.ts`):
- ورقة طباعة واحدة: لون الكرتون مع هامش قص 3 مم، والشعار (من تبويب الملصق)، واسم الدار بالفويل، واسم العطر والتفاصيل.
- كل وجه مدوَّر ليُقرأ معتدلاً بعد الطي.
- مناطق اللصق تبقى بلا حبر.
- **الورقة نفسها هي خامة المجسم**: ما يراه العميل مطويّاً هو ما سيُطبع.

**الملفات** (`export.ts`):
- **PDF**:
  - الصفحة 1: التصميم بمقاسه الحقيقي (حتى 300 نقطة/بوصة)، وفوقه خط القص للتحقق من التموضع.
  - الصفحة 2: القص بالماجنتا، والتكسير بالسماوي المتقطع، واللصق مظلل.
- **SVG بالمليمتر** بطبقات مسمّاة (CUT / CREASE / GLUE / INFO) لبرامج التصميم وطاولات القص.

**المقاسات:**
- المقاس داخلي، و«ملاءمة للعبوة المختارة» تحسبه من العبوة وغطائها مع هامش حشوة.
- تُعرض للعميل ثلاث قيم: المقاس الخارجي، وأبعاد الفرخ المسطّح، ومساحة الكرتون (مفيدة للتسعير).

**الحفظ:** التصميم يُحفظ في المتصفح، ويُضاف إلى ملخص التركيبة المرسل للخبير.

**الاختبارات** (191 فحصاً على الأنواع الخمسة بثلاثة مقاسات):
- كل حافة إما قص أو تكسير.
- لا تداخل بين الألواح.
- **المجسم المطوي يُغلق على المقاس الخارجي المعلن بدقة السماكة.**
- الفتح والإغلاق يعيدان الشكل نفسه.

> `src/studio/stage.ts` خشبة عرض مشتركة بين عارض العبوة وعارض العلبة: الإضاءة والكاميرا والرسم عند الحاجة.

## استوديو المبدعين (المرحلة 5)
صفحتان عامتان، وقسم لإدارتهما في لوحة الإدارة:
- **`/creatives`**: دليل المصممين مع تصفية حسب التخصص، ومعرض الأعمال، ونموذج «اطلب مصمماً».
- **`/creatives/:slug`**: ملف المصمم: النبذة، وسنوات الخبرة، ومدة التسليم، والسعر المبدئي، وأعماله، ونموذج طلب موجّه إليه مباشرة.
- **`/admin/creatives`**: إدارة المصممين وأعمالهم، وتتطلب صلاحية `studio.manage` (المصمم والمدير والمالك).

**التخصصات الستة:** هوية بصرية، ملصقات، تغليف وعلب، عبوات، تصيير ثلاثي الأبعاد، تصوير منتجات.

**المعرض:**
- عارض بملء الشاشة يتنقّل بين صور العمل الواحد ثم بين الأعمال.
- الأسهم تتبع اتجاه اللغة: السهم الأيسر هو «التالي» في العربية. ويدعم السحب باللمس.
- Esc يغلقه ويعيد التركيز إلى العنصر الذي فتحه.

**الصدق في العرض:**
- كل عمل يُعلَّم «مشروع تصوّري» أو يُذكر اسم عميله (بإذنه).
- الملفات الثلاثة المرفقة للعرض **توضيحية** وتحمل شارة ظاهرة للزائر. احذفها من `/admin/creatives` عند إضافة مصمميكم.
- قاعدة Supabase تبدأ فارغة: لا مصممين وهميين في الإنتاج.

**طلب التصميم:**
- يصل إلى صندوق الوارد كنوع جديد `design` في تبويب «تصميم».
- يُربط تلقائياً بملف العميل في الـCRM.
- يحمل المصمم المطلوب والخدمة والميزانية والموعد.
- زر «أكملها مع مصمم» في استوديو 3D يرفق ملخص التركيبة ورابطها. الرابط يُقبل فقط إن كان من الموقع نفسه.

**الصور:**
- تُصغَّر في المتصفح قبل الرفع: أقصى ضلع 1600 بكسل بصيغة WebP.
- حتى 12 صورة للعمل، والأولى هي الغلاف، ويمكن إعادة ترتيبها.
- التخزين في حاوية `portfolio` على Supabase Storage: القراءة عامة، والرفع لـ`studio.manage` فقط. في الوضع التجريبي تُحفظ في IndexedDB.

**قاعدة البيانات** (جدولا `creatives` و`creative_works`):
- الزائر يرى المنشور فقط، ولا يرى عملاً لمصمم غير منشور.
- روابط الصور https فقط.
- الحذف يتسلسل من المصمم إلى أعماله.
- كل إنشاء ونشر وحذف يُسجَّل في سجل التدقيق.

## محتوى الموقع — CMS (المرحلة 6)
`/admin/cms` لصلاحية `content.edit` (المحرر والمدير والمالك). خمس وثائق، قيمها الافتراضية هي المحتوى الحالي في الكود:

| الوثيقة | ما تتحكم به | أين يظهر |
|---|---|---|
| التواصل والحسابات | البريد، الجوال، واتساب، العنوان، ساعات العمل، 5 حسابات | صفحة التواصل، التذييل، زر واتساب العائم |
| شريط الإعلان | تفعيل، نص، رابط وزر، لون، تاريخ انتهاء | أسفل الصفحات العامة |
| واجهة الرئيسية | العنوان بأسطره، الوصف، الأزرار، الصورة، الأرقام الأربعة | الرئيسية + أرقام «عن المنصة» |
| الأسئلة الشائعة | إضافة، حذف، ترتيب، إخفاء، الموضوع | الرئيسية (أول 5)، صفحة الأسئلة، صفحات الخدمات |
| المكالمة والعينة | مدة المكالمة، الأيام، المواعيد، أيام الحجز؛ عدد العينات وحجمها ومدة الخصم والشحن | `/book`، `/discovery-kit` |

**دورة العمل:**
1. **عدّل.**
2. **احفظ كمسودة.** المسودة لا يراها أحد.
3. **عاين في الموقع.** يُفتح تبويب يعرض المسودات لك وحدك، مع شارة «معاينة».
4. **انشر.**

- كل نشر يُحفظ نسخةً (آخر 30). «استرجاع» يعيد النسخة **كمسودة** لتراجعها قبل النشر، ولا يغيّر الموقع مباشرة.
- يُنبَّه المحرر قبل مغادرة تعديلات غير محفوظة.

**الأمان والمتانة:**
- كل قيمة تمر عبر `sanitize()` في `src/cms/schema.ts`:
  - روابط الحسابات https فقط.
  - الروابط الداخلية لا تبدأ بـ`//`.
  - الأرقام مقيّدة بحدود.
  - المواعيد بصيغة HH:MM.
- أي حقل تالف يعود لقيمته الافتراضية، فلا يكسر خطأ إدخال الموقع.
- المنشور يقرؤه الجميع. المسودات والنسخ لـ`content.edit` فقط.
- النشر والاسترجاع دالتان على الخادم (`publish_content` و`restore_content_version`) تسجّلان في سجل التدقيق. لا كتابة مباشرة على المحتوى المنشور.
- المحتوى المنشور يُخزَّن في المتصفح، فتُرسم الزيارة التالية بالنص الصحيح فوراً بلا ومضة للنص القديم.

> **سعر عينة الاكتشاف لا يُعدَّل من CMS عمداً:** الخادم يتحقق من المبلغ عند الدفع (`KIT_PRICE_HALALAS`). غيّره في `src/config/offers.ts` وفي متغير البيئة معاً.

## لوحة العميل والاعتمادات (المرحلة 7)
لوحة العميل `/account` تعرض الآن بياناته الحقيقية بدل البيانات النموذجية، وصفحات الرسائل والفواتير النموذجية تُحوَّل إليها.

**ما يراه العميل:**
| الصفحة | المحتوى |
|---|---|
| `/account` | ما ينتظر اعتماده، ومشاريعه بمراحلها الخمس (الملخص ← التصميم ← العينات ← الإنتاج ← التسليم) |
| `/account/projects/:id` | التصاميم بنسخها، و«اعتماد» أو «طلب تعديل» (الملاحظة إلزامية)، والنقاش مع الفريق، وإرسال تصميم من حسابه |
| `/account/approvals` | كل ما ينتظر قراره، وقراراته الأخيرة |
| `/account/designs` | تصاميم استوديو 3D المحفوظة في حسابه |

**التصاميم المحفوظة:**
- زر «احفظ في حسابي» في `/studio-3d` يحفظ إعدادات العبوة والملصق والعلبة مع صورة مصغّرة.
- «فتح في الاستوديو» يعيدها كما حُفظت، من أي جهاز.

**ما يراه الفريق** (`/admin/projects`):
- **إنشاء مشروع**: لصلاحية `projects.manage` (المبيعات والإدارة)، من القائمة أو من ملف العميل في الـCRM.
- **الربط بالعميل**: بالبريد. يرى العميل مشروعه فوراً، أو عند تسجيله لاحقاً بالبريد نفسه.
- **إرسال تصميم للاعتماد**: صور أو PDF (حتى 12 ملفاً). «نسخة جديدة» ترقّم النسخة تلقائياً وتجعل السابقة «نسخة سابقة»، فلا يبقى إلا قرار واحد معلّق لكل تصميم.
- **من يرى ماذا**:
  - **المصمم** يرى المشاريع المسندة إليه فقط ويرفع لها، بعد أن أُزيلت عنه صلاحية عرض كل المشاريع.
  - **الإنتاج** يرى كل المشاريع دون رفع.
  - **المحرر** لا يرى المشاريع.
- **التنبيه في القائمة الجانبية**: شارة بعدد طلبات التعديل التي تنتظر الفريق.

**الأمان** (`supabase/schema.sql`):
- الدالة `project_access()` تحدد علاقة المستخدم بكل مشروع، وكل سياسات الوصول مبنية عليها.
- **قرار العميل** عبر `decide_item()` فقط، ولا تعديل مباشر على الحالة. العميل وحده يقرر، ولا يقرر الفريق نيابةً عنه.
- **الحقول الحساسة يفرضها الخادم**:
  - الحالة، والنسخة، والكاتب، و«من العميل».
  - ما يرسله العميل يكون «أرسله العميل» دائماً، ولا يُعامَل كتصميم للاعتماد.
- **الملفات** في حاوية `projects` **خاصة**، تُعرض بروابط موقّعة مؤقتة (ساعة). مسار الملف يبدأ بمعرّف المشروع لتطبّق صلاحياته.
- **السجلات**:
  - كل قرار ونسخة وتغيير مرحلة يُسجَّل في سجل التدقيق وفي نشاط العميل بالـCRM.
  - النقاش لا يُعدَّل ولا يُحذف.

> **قبل الإطلاق:** فعّل «تأكيد البريد» في Supabase Auth. الربط بالبريد يفترض أن صاحب الحساب يملك البريد فعلاً.

## سعر العلبة لحظياً (ربط الاستوديو بحاسبة التكلفة)
في تبويب «العلبة» بـ`/studio-3d` يرى العميل **السعر التقديري للعلبة** يتغيّر مع كل قرار: النوع، والمقاس، ولون الكرتون، والتشطيب، والفويل، والكمية. يظهر السعر في بطاقة اللوحة وبجانب المعاينة ثلاثية الأبعاد.

**المعادلة** (`src/studio/box/pricing.ts`) تحسب من **مخطط القص نفسه** لا من تقدير عام:
- **متغيرة لكل علبة**:
  - الكرتون: مساحة الفرخ × سعر خامة النوع × الهدر.
  - الطباعة: لون كامل للكرتون الأسود والملوّن، ونص فقط للفاتح.
  - التشطيب: مطفأ، أو مخملي، أو لامع.
  - الفويل.
  - التجميع واللصق.
- **تجهيز لمرة واحدة**: قالب القص بطول خطوط القص والتكسير، وألواح الطباعة، وكليشة الفويل.
- **سعر العلبة** = المتغيرة × (1 − خصم الكمية) + التجهيز ÷ الكمية. شرائح الخصم هي نفسها في الحاسبة.
- **تنبيهات**: يُنبَّه العميل إن كانت الكمية تحت الحد الأدنى لنوع العلبة، ويرى سعر الشريحة التالية.

**الحاسبة** (`/pricing`):
- إن كان للزائر علبة من الاستوديو، تحل تكلفتها الفعلية محل تقدير «العلبة والتغليف» العام (8 ر.س)، ويُضاف تجهيزها مرة واحدة للإجمالي.
- يستطيع الزائر إيقاف ذلك، أو الانتقال للاستوديو لتعديل العلبة.

**الأسعار تجارية وتُعدَّل من `/admin/cms` ← «أسعار العلب»**:
- **ما يُضبط**: سعر الخامة والتجميع والحد الأدنى لكل نوع، والطباعة والتشطيب، والفويل، والتجهيز.
- **مثال حي** يُظهر أثر كل تغيير على سعر علبة نموذجية بالأنواع الخمسة.

> القيم الافتراضية تقديرات للتخطيط في السوق السعودي (علبة بلسان ≈ 2.2 ر.س، صلبة ≈ 8.6، مغناطيسية ≈ 9.2 ر.س بألف قطعة). **عايرها على عروض موردي الكرتون والمطابع قبل عرضها على العملاء.**

## «ابدأ مسارك»: الملخص قبل الحساب

زر «ابدأ هذا المسار» و«اطلب هذه الباقة» في صفحة كل خدمة يفتحان `/start/<A–F>` (والباقة مختارة مسبقاً عبر `?package=`).

| الخطوة | ما يراه العميل | ما يحدث |
|---|---|---|
| 1 · مشروعك | 4–5 أسئلة اختيار خاصة بالخدمة + تفاصيل اختيارية (اسم البراند، الفكرة، رابط مرجع) | المسودة تُحفظ في التبويب، فالتحديث لا يضيّعها |
| 2 · بياناتك | الاسم، البريد، الجوال السعودي — **بلا كلمة مرور** (العميل المسجّل يرى بياناته فقط) | طلب `brief` في صندوق الوارد، يُنشئ عميلاً في CRM تلقائياً |
| 3 · تم | تأكيد + «اختر كلمة مرور فقط» لمتابعة الطلب | عند الدخول بالبريد **المؤكَّد** يتحول الطلب إلى مشروع في مرحلة «الملخص» ويُفتح مباشرة |

- الأسئلة في `src/start/briefs.ts`؛ الباقات تُقرأ من بيانات الخدمة نفسها.
- التحويل إلى مشروع على الخادم فقط: `claim_briefs()` تطابق بريد الجلسة المؤكَّد، مرة واحدة لكل طلب، وأقصى 5 طلبات في المرة؛ لا يستطيع أحد المطالبة بطلب بريد غيره، والزائر لا يستدعيها.
- `leads.project_id` لا يضبطه المتصفح (يُصفَّر عند الإرسال، ولا يعدّله الفريق يدوياً).
- المشروع الناتج بلا مسؤول من الفريق حتى يُسند؛ الملخص يظهر بالصياغة نفسها للعميل (صفحة مشروعه) وللفريق (صندوق الوارد ← تبويب «بدء مسار»، وصفحة المشروع).
- إن كان البريد مسجّلاً: يُطلب منه الدخول ويجد طلبه مشروعاً في حسابه. إن كان تأكيد البريد مفعّلاً: يتحول الطلب بعد التأكيد والدخول.

## مراحل خاصة بكل مسار

مراحل المشروع تتبع خطوات الخدمة نفسها (`src/data/services.ts`)، مع مدة كل مرحلة، ثم «التسليم» للجميع:

| المسار | المراحل |
|---|---|
| براند كامل | البريف والاستراتيجية ← التركيبة والعينات ← الهوية والعبوة ← التصنيع والإطلاق ← التسليم |
| تطوير عطر | البريف ← الجولة الأولى ← التحسين ← الاعتماد ← التسليم |
| عبوة وتغليف | الاتجاه ← التصميم ← النموذج ← التسليم |
| هوية بصرية | الاستكشاف ← المفاهيم ← النظام ← التسليم |
| تصنيع | مراجعة الملفات ← التوريد ← الإنتاج ← التسليم |
| طباعة وتنفيذ | فحص الملفات ← البروفة ← الطباعة ← التسليم |
| بلا مسار | الملخص ← التصميم ← العينات ← الإنتاج ← التسليم |

- المفاتيح في `src/projects/stages.ts` ومطابقة لـ`track_stages()` في قاعدة البيانات؛ القيد `projects_stage_ok` يرفض مرحلة لا تخص مسار المشروع.
- تغيير مسار مشروع من الإدارة ينقل مرحلته لما يقابل موضعها؛ وتطبيق المخطط يرحّل المشاريع القائمة بالطريقة نفسها.
- سجل نشاط العميل في CRM يكتب اسم المرحلة بالعربية (`stage_label()`).

## إشعار فوري للفريق بكل طلب (`api/lead-notify.ts`)

كل طلب يصل من الموقع (بدء مسار، حجز، عينة، تصميم، رسالة) يصل للفريق خلال ثوانٍ، برسالة فيها: من، وكيف نتواصل معه، وما يريد (إجابات «ابدأ مسارك» مقروءة)، ورابط يفتح الطلب في صندوق الوارد.

1. في Vercel أضف `LEAD_WEBHOOK_SECRET` (سلسلة عشوائية 32 حرفاً فأكثر) و`SITE_URL`، ثم قناة واحدة على الأقل:
   - **واتساب** (WhatsApp Cloud API): `WHATSAPP_TOKEN`، `WHATSAPP_PHONE_NUMBER_ID`، `NOTIFY_WHATSAPP_TO` (مثل `966550001111`)، و`WHATSAPP_TEMPLATE`: قالب «Utility» معتمد لدى Meta بمتغير نصي واحد في المتن، مثل: «طلب جديد في المنصة: {{1}}».
   - **البريد** (Resend): `RESEND_API_KEY`، `NOTIFY_EMAIL_TO`، `NOTIFY_EMAIL_FROM` (من نطاق موثّق).
   - **Slack أو Discord أو Make/Zapier**: `NOTIFY_WEBHOOK_URL` (https).
2. في Supabase: Database ← Webhooks ← Create: الجدول `leads`، الحدث Insert، طلب HTTP بطريقة POST إلى `https://<نطاقك>/api/lead-notify`، وترويسة `x-webhook-secret` بنفس قيمة السر.
3. أرسل طلباً تجريبياً من `/start/A` وتأكد من وصوله.

الطلب يُحفظ في قاعدة البيانات قبل الإشعار؛ فشل قناة لا يضيّع طلباً، والقنوات الأخرى تُرسَل رغم فشل إحداها. النشرة البريدية لا تُشعر (`NOTIFY_KINDS` لتغيير الأنواع).

## عرض السعر والعربون

من صفحة المشروع في الإدارة: «أنشئ عرض السعر» ← بنود (وصف، كمية، سعر وحدة) ← العربون ٪ وتاريخ الصلاحية والشروط ← «حفظ وإرسال للعميل».

| الخطوة | العميل | الفريق | ما يحدث تلقائياً |
|---|---|---|---|
| مسودة | لا يراها | يحرر ويرى المجاميع لحظياً | — |
| إرسال | يرى العرض في مشروعه وفي «بانتظار اعتمادك» | العرض يُقفل (للتعديل: «عرض محدّث» يلغي السابق) | صفقة CRM ← «عرض سعر» وقيمتها = الإجمالي |
| اعتماد أو طلب تعديل | زر واحد؛ التعديل بملاحظة تصل للنقاش | يرى الملاحظة على العرض | — |
| العربون | مويسر داخل الصفحة، أو تحويل بنكي (الآيبان من «محتوى الموقع») | «تسجيل دفعة مستلمة» للتحويل والنقد | المشروع ينتقل من الملخص لمرحلته الثانية، والصفقة «مكسوبة» |

- ضريبة القيمة المضافة 15% تُحفظ مع كل عرض؛ المبالغ يحسبها الخادم (`quote_before`) والمعاينة في المتصفح مطابقة لها حتى الهللة.
- دفعة مويسر لا تُعتمد من رابط العودة: `api/payments/verify.ts` يجلبها بالمفتاح السري، ويطابق مبلغها مع عربون العرض في قاعدة البيانات، ثم يسجّلها عبر `record_deposit` (مفتاح الخدمة فقط، ولا تُسجَّل دفعتان لعرض واحد). يلزم `SUPABASE_URL` و`SUPABASE_SERVICE_ROLE_KEY` في Vercel.
- بيانات الفوترة (الاسم النظامي، الرقم الضريبي، السجل التجاري، البنك، الآيبان) من «محتوى الموقع ← معلومات التواصل»، وتظهر في العرض.
- **ملاحظة نظامية:** عرض السعر ليس فاتورة ضريبية. إصدار الفواتير الإلكترونية (فاتورة — المرحلة الثانية) يتطلب الربط بمنصة هيئة الزكاة والضريبة والجمارك أو بمزوّد معتمد.

## التقارير وعروض الأسعار (`/admin/reports`، `/admin/quotes`)

حلّتا محل صفحات «الطلبات» و«التقارير» و«الإعدادات» النموذجية (الروابط القديمة تحوّل إليهما وإلى «محتوى الموقع»). متاحتان لمن لديه `payments.view` (المالك، المدير، المبيعات).

**التقارير** — الفترة 7 أو 30 أو 90 يوماً:
- **القمع:** طلبات «ابدأ مسارك» في الفترة، وإلى أين وصلت: حساب ← عرض سعر ← اعتماد ← عربون. أكبر تسرب بين خطوتين يُعلَّم.
- **المؤشرات:** المحصّل (عربون العروض + مدفوعات مويسر الأخرى، دون احتساب العربون مرتين)، عدد العروض ونسبة تحولها لعربون، متوسط قيمة العرض، ووسيط زمن إرسال العرض.
- **يحتاج تدخلاً اليوم:** من بدأ مساراً ولم ينشئ حساباً، مشروع بلا عرض بعد يومين، طلب تعديل عرض، عرض بلا رد بعد 3 أيام، عرض معتمد بلا عربون — كل بند يفتح مكانه.
- حسب المسار، والمحصّل أسبوعياً لآخر 8 أسابيع.

الحسابات في `src/admin/reports/metrics.ts` (دالة نقية مختبرة).

**عروض الأسعار:** كل العروض عبر المشاريع، بفلاتر الحالة والبحث وتصدير CSV (بالمجاميع والضريبة والعربون ومرجع الدفع).

## إشعار العميل و«خطوتك التالية»

**`api/client-notify.ts`** يخبر العميل بالبريد وواتساب حين يحتاجه المشروع:

| الحدث | الرسالة |
|---|---|
| أرسل الفريق تصميماً للاعتماد | «تصميم بانتظار اعتمادك» مع رابط يفتح التصميم نفسه |
| أُرسل عرض سعر | رقم العرض وإجماليه شامل الضريبة |
| دُفع العربون | تأكيد الاستلام وبدء العمل |
| تغيّرت مرحلة المشروع | اسم المرحلة الجديدة (حسب المسار) والتي تليها |

الإعداد: ثلاثة Webhooks في Supabase (Database ← Webhooks) بطريقة POST إلى `https://<نطاقك>/api/client-notify` وبترويسة `x-webhook-secret` (نفس `LEAD_WEBHOOK_SECRET`):
`project_items` عند Insert، و`project_quotes` عند Update، و`projects` عند Update. ويلزم `SUPABASE_URL` و`SUPABASE_SERVICE_ROLE_KEY` و`SITE_URL`، وقناة على الأقل: البريد (`RESEND_API_KEY`، `NOTIFY_EMAIL_FROM`) أو واتساب (`CLIENT_WHATSAPP_TEMPLATE`: قالب Utility معتمد بمتغير نصي واحد). الجوال يُقرأ من ملف العميل في CRM ويُحوَّل لصيغة 9665xxxxxxxx.

الدالة لا تثق بالحدث إلا في معرّف المشروع؛ العنوان والمستلم من قاعدة البيانات. تصاميم العميل نفسه وتحديثات الحالة الداخلية لا تُرسل شيئاً.

**«خطوتك التالية»** أعلى لوحة العميل: إجراء واحد واضح بالأولوية — العربون (يبدأ العمل)، ثم عرض السعر، ثم التصاميم، الأقدم أولاً — والباقي تحته. وإن لم يكن شيء: «لا شيء مطلوب منك الآن» مع المرحلة التي يعمل عليها الفريق. شارة «بانتظار اعتمادي» تعدّ الشيء نفسه (`src/projects/next.ts`).

## التسعير والربحية والمخزون

### الصلاحيات
| الصلاحية | الأدوار | ماذا تفتح |
|---|---|---|
| `pricing.manage` | المالك، المدير | قائمة الأسعار العامة (وثيقة «الأسعار»)، سياسة الخصم والهامش، الكوبونات |
| `inventory.view` | المالك، المدير، المبيعات، الإنتاج | رؤية المخزون (المبيعات تربط البنود بمواده في العروض) |
| `inventory.manage` | المالك، المدير، الإنتاج | إضافة المواد، الاستلام، الصرف، الحجز، تسوية الجرد |

### المخزون (`/admin/inventory`)
- المادة: رمز SKU، الفئة، الوحدة، حد إعادة الطلب، المورّد.
- **الرصيد ومتوسط التكلفة لا يُكتبان باليد**: تحسبهما الحركات على الخادم (`inventory_move_apply`). الاستلام بتكلفة الوحدة يحدّث **المتوسط المرجّح**؛ الحركات سجل للإضافة فقط، والتصحيح بحركة «تسوية جرد» بسبب إلزامي.
- **الحجز**: عند دفع عربون عرض فيه بنود مربوطة بمواد، تُحجز الكميات للمشروع تلقائياً؛ «المتاح» = الرصيد − المحجوز (السالب = عجز يظهر في التقارير).
- **الصرف** من صفحة المشروع (أو المخزون) يُنقص الرصيد والمحجوز، ويسجّل **تكلفة المواد على المشروع** بمتوسط التكلفة لحظة الصرف.

### التكلفة والهامش في عرض السعر
- لكل بند **تكلفة وحدة داخلية** (تُملأ تلقائياً من متوسط تكلفة المادة إن رُبط بالمخزون) + «تكاليف أخرى»؛ تُحفظ في `quote_costs` التي **لا يقرؤها العميل**.
- المحرر يعرض الربح المتوقع ونسبته لحظياً، وينبّه حين يقل عن **حد الهامش**.
- **الخصم** نسبة أو مبلغ قبل الضريبة، ويظهر للعميل بنداً واضحاً. **سقف الخصم لكل دور** (افتراضياً المبيعات 10%) يفرضه الخادم عند الإرسال: ما فوقه يُحفظ مسودة ويرسله المالك أو المدير.
- **التكاليف الفعلية** للمشروع (مواد مصروفة تلقائياً + مصنع، تصميم، شحن…) والربح الفعلي حتى الآن في صفحة المشروع.

### قائمة الأسعار (وثيقة «الأسعار» في محتوى الموقع)
أرقام الحاسبة (تكلفة كل عنصر، شرائح خصم الكمية، مضاعفات السرعة، جولات العينات والتصميم، مضاعف التجزئة)، «يبدأ من» لكل مسار، **سعر عينة الاكتشاف** (يتحقق به الخادم عند الدفع بدل `KIT_PRICE_HALALAS`)، وأسعار العلب. مسودة ← معاينة ← نشر، بنسخ قابلة للاسترجاع.

### الكوبونات (`/admin/pricing`)
كود، نسبة أو مبلغ، تاريخ انتهاء، حد استخدام. تُطبَّق على عينة الاكتشاف عند الدفع: السعر بعد الكوبون يحسبه الخادم (`coupon_price`)، ويُسجَّل الاستخدام مرة لكل دفعة بعد التحقق منها لدى مويسر (`redeem_coupon`). للمشاريع يُستخدم خصم عرض السعر.

### في التقارير
الإيراد بعد الخصم، الربح المتوقع (من تكلفة العروض) والفعلي (من التكاليف المسجلة) ونسبتهما مقابل الحد، الربح المتوقع لكل مسار، والعروض تحت الحد والمواد التي تحتاج إعادة طلب ضمن «يحتاج تدخلاً اليوم».

## الصفحات القانونية (`/privacy`، `/terms`، `/refund`)

نصوص افتراضية للخصوصية (نظام حماية البيانات الشخصية) والشروط والإلغاء والاسترجاع (نظام التجارة الإلكترونية) في `src/data/legal.ts`، وتُعدَّل من «محتوى الموقع ← الصفحات القانونية» بمسودة ونشر وسجل نسخ ككل وثائق المحتوى. المتغيرات `{legalName}` `{cr}` `{vat}` `{email}` `{phone}` `{address}` `{kitCreditDays}` تُملأ من «التواصل والحسابات» و«المكالمة والعينة»، فلا يتكرر إدخال بيانات المنشأة.
روابطها في تذييل الموقع (مع السجل والرقم الضريبي متى أُدخلا)، وسطر موافقة قرب كل زر إرسال ودفع: إنشاء الحساب، «ابدأ مسارك»، الحجز، دفع العينة، واعتماد عرض السعر.
**النصوص صياغة مبدئية ويجب أن يراجعها مستشار قانوني قبل الإطلاق.**

## الحماية من الرسائل المزعجة

- **حدود على الخادم (دائماً)**: المُشغّل `lead_flood_guard` يرفض الطلب برسالة «محاولات كثيرة» إن تجاوز 5 طلبات لكل عنوان IP كل 10 دقائق (30 يومياً)، أو 3 لكل بريد، أو 200 طلب من كل الزوار كل 10 دقائق. `coupon_price` يقبل 10 محاولات كوبون لكل عنوان كل 10 دقائق. العنوان من `cf-connecting-ip` (Supabase خلف Cloudflare). الأحداث في `rate_events` وتُنظَّف تلقائياً.
- **حقل خفي (honeypot)** في النماذج يتجاهل الروبوتات البسيطة بصمت.
- **التحقق البشري (اختياري)**: أنشئ موقعاً في Cloudflare Turnstile، وضع `VITE_TURNSTILE_SITE_KEY` (للواجهة) و`TURNSTILE_SECRET_KEY` (للخادم) في متغيرات Vercel. عندها يرسل الزائر غير المسجّل طلبه عبر `api/lead.ts` الذي يتحقق من الرمز ثم يحفظ الطلب بمفتاح الخدمة مع عنوان الزائر الحقيقي (فتبقى الحدود فعّالة). الأداة لا تظهر إلا لمن يشتبه به.
  ولإغلاق الإدخال المباشر في قاعدة البيانات أمام الزوار نهائياً فعّل «إلزام الزوار بالتحقق البشري» من «التسعير والربحية ← الحماية من الرسائل المزعجة» (يُخزَّن `captcha_required` في `business_settings`).

## «عطرك الخاص» للأفراد (`/bespoke`)

خدمة مستقلة عن مسارات البراندات: فرد يكوّن عطره الشخصي ويضبطه مع مستشار تكوين.

1. **التكوين**: 32 مكوناً في مكتبة (`src/bespoke/notes.ts`) موزعة على المقدمة والقلب والقاعدة (حتى 3 في كل طبقة)، منها مكونات محلية (ورد طائفي، عود كمبودي وهندي، لبان ظفاري، بخور، مسك الطهارة، هيل، زعفران). أربع أفكار جاهزة للبدء، وتصفية بالعائلة العطرية.
2. **قراءة فورية** (`src/bespoke/compose.ts`): هرم العطر، الطابع بالنسب، القوة، الثبات التقديري، التوليفات الكلاسيكية (✓)، والتنبيهات (مكونات طاغية، عودان معاً، تضادات صعبة) — التنبيه لا يمنع الإرسال بل يصل للمستشار. التركيز (أو دو بارفان، إكستريه، دهن) والحجم والاسم المنقوش على الزجاجة.
3. **السعر التقديري** = الحجم × سعر المل للتركيز + الزجاجة والعلبة والنقش + إضافة لكل مكوّن نادر. الأرقام في «محتوى الموقع ← قائمة الأسعار ← عطرك الخاص». السعر النهائي في عرض السعر بعد الجلسة.
4. **جلسة المستشار (مجانية)**: مكالمة فيديو أو واتساب أو زيارة الاستوديو، بموعد من جدول «المكالمة والعينة». بعد الإرسال زر «تحدث مع المستشار الآن» يفتح واتساب برسالة تحمل التركيبة.
5. **في النظام**: الطلب بريف للمسار `P` فيصبح مشروعاً في حساب العميل (`claim_briefs`) بمراحل: التكوين والاستشارة ← العينات التجريبية ← التعبئة والنقش ← التسليم. المستشار هو مسؤول المشروع: يحادث العميل في صفحة المشروع، يرفع العينات للاعتماد، ويرسل عرض السعر بالعربون كبقية المسارات. التركيبة تظهر بأسماء المكونات في صندوق الوارد وملخص المشروع وإشعار الفريق.

## العقود (`project_contracts`)

العقد جزء من المشروع، يكتبه المصنع (الفريق) ويوقّعه الطرفان إلكترونياً:

1. **الإنشاء** من صفحة المشروع في الإدارة ← «أنشئ عقداً»: قالب بنود تصنيع وتوريد (`src/contracts/template.ts`) مملوء من المشروع وعرض السعر المعتمد (القيمة، العربون، رقم العرض، الموعد) وبيانات المنشأة (الاسم النظامي، السجل).
2. **التحرير**: العنوان، بيانات الطرفين، البنود (إضافة وحذف وترتيب)، و**ملحق المواصفات والكميات**: لكل صنف اسمه ومواصفاته وكميته ووحدته وحتى 8 صور و4 ملفات PDF تُرفع لمجلد المشروع الخاص. الأصناف تُملأ مبدئياً من بنود عرض السعر.
3. **الإرسال**: يُقفل النص وتُحسب له بصمة SHA-256 على الخادم. يصل العميل إشعار (Webhook على `project_contracts` ← Update إلى `api/client-notify`) ويظهر في «خطوتك التالية».
4. **العميل** يقرأ العقد والملحق بصوره، ثم إما «طلب تعديل» بملاحظة (تصل نقاش المشروع ويعود العقد قابلاً للتحرير) أو **التوقيع**: اسمه الكامل + إقرار + توقيع يرسمه بإصبعه/الفأرة أو صورة توقيع يرفعها.
5. **المنشأة** توقّع بنفس الطريقة — صلاحية `contracts.sign` (المالك والمدير). يكتمل العقد «موقّعاً من الطرفين» بأي ترتيب.
6. **النسخة الموقّعة**: `/contract/<id>` للطرفين فقط، للطباعة أو الحفظ PDF من المتصفح، وفيها التوقيعان وتاريخهما والبصمة.

الضمانات على الخادم: كل توقيع مربوط ببصمة النص الذي رآه صاحبه (تغيّر النص = رفض التوقيع)؛ لا تعديل بعد الإرسال إلا بإعادته للتحرير قبل توقيع العميل (ويُمسح توقيع المنشأة المسبق)؛ الصور والتوقيعات من مجلد المشروع فقط؛ العميل لا يرى المسودات؛ إلغاء العقد الموقّع لمن يملك التوقيع عن المنشأة فقط؛ كل خطوة في سجل التدقيق وسجل العميل، ويُحفظ عنوان IP للعميل عند توقيعه.
**القالب صياغة مبدئية يراجعها مستشار قانوني قبل الاعتماد.**
